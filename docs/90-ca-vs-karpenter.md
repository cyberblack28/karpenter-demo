# 90. Cluster Autoscaler と Karpenter の比較（リファレンス）

デモの必須手順ではありませんが、**発表時の質疑応答や、導入判断の材料**として使えるよう、
両者の違いを詳しくまとめたものです。概要だけ知りたい場合は [00-overview.md](00-overview.md) で十分です。

## ひとことで言うと

| | 仕組み |
| --- | --- |
| **Cluster Autoscaler（CA）** | 「**既存のノードグループの台数を増減する**」仕組み |
| **Karpenter** | 「**Pod の要件に合うノードを動的に設計・作成し、ライフサイクルまで管理する**」仕組み |

## 共通していること

どちらも **スケジュールできない Pod を検出してノードを追加**し、
**不要になったノードを削除・統合**できます。この基本的な目的は同じです。

## 比較表

| 観点 | Cluster Autoscaler | Karpenter |
| --- | --- | --- |
| **基本モデル** | 事前に作成されたノードグループのサイズを変更 | NodePool の制約から、必要な個別ノードを動的に作成 |
| **ノード選択** | 複数の既存ノードグループから最適なものを選択 | Pod の CPU・メモリ、Affinity、Taint/Toleration、Zone、アーキテクチャなどから適切なノードを選択 |
| **スケールイン** | 不要なノードをノードグループから削除 | 空ノード削除、集約、より安価なノードへの置換 |
| **ライフサイクル管理** | 基本的にスケーリングのみ | Consolidation、Drift、Expiration、中断対応なども管理 |
| **クラウド対応** | 対応プロバイダーが多い | Provider 実装が必要で、機能や成熟度が Provider ごとに異なる |
| **主な特徴** | Group-based autoscaling | Group-less / auto-provisioning |

---

## Cluster Autoscaler

### できること

- Pending Pod を収容できる既存ノードグループを選び、ノード数を増やす
- Pod を別ノードへ移動できる場合、不要なノードを削除する
- 複数のノードグループを 1 つの CA で管理する

### できない・苦手なこと

- **事前定義されていない新しいノード構成を、その場で作成すること**
- ノードイメージ更新、一定期間経過後の入れ替えなど、**ノードのライフサイクル全体の管理**
- 多数のインスタンスタイプ、Zone、GPU、Spot／オンデマンドなどを柔軟に組み合わせる場合、
  **ノードグループ数が増えやすい**

### メリット

- 既存の Managed Node Group や Auto Scaling Group と親和性が高い
- ノード構成が固定されるため、**動作やコストを予測しやすい**
- 対応するクラウドプロバイダーが比較的多い

### デメリット

- ワークロードが多様になるほどノードグループが増え、**管理が複雑になる**
- 既存グループ単位でしか選択できないため、**キャパシティ選択の粒度が粗い**

---

## Karpenter

### できること

- Pending Pod の要求を解析し、**適切なインスタンスタイプや Zone などを動的に選択**する
- ノードグループを事前に大量作成せず、**少数の柔軟な NodePool で多様なノードを作成**する
- 空ノードの削除、ノード集約、**より安価なノードへの置換**を行う
- **Drift、Expiration、Spot 中断**などに応じてノードを入れ替える

### できない・苦手なこと

- 対応するクラウド **Provider 実装がなければ利用できない**
- 既存ノードグループの desired size を増減することが主目的ではない
- **Provider 固有の権限、NodeClass、ネットワーク、イメージなどの設計が必要**
- Consolidation や Drift を積極的に設定するとノード交換が増えるため、
  **Disruption Budget や PDB の設計が必要**

### メリット

- ノードグループの乱立を抑えられる
- 多様なワークロードや**急激な負荷変動に対応しやすい**
- Spot を含む幅広いキャパシティから選択し、**コストを最適化しやすい**
- スケーリングだけでなく**ノードの更新・交換も自動化**できる

### デメリット

- CA よりも**設定・権限・障害解析の範囲が広い**
- Consolidation や Drift により、**意図しないタイミングで Pod が再配置される可能性がある**
- 利用可能な機能やサポート範囲が**クラウド Provider 実装に依存する**

> **実例**：本デモでも、OKE の CNI が VCN-Native だったために
> `OCINodeClass` のセカンダリ VNIC 設計が必要になりました。
> これは「Provider 固有の設計が必要」の具体例です（[99](99-troubleshooting.md)）。

## 補足：CA の「ノード置き換え」はどこまでできるか

「8 CPU のノードに Pod が 1 つだけ」という無駄な状態を例に、両者の差を掘り下げます。
**CA でも状況によっては解消できます**が、条件が付きます。

**ケースA：小さいノードが既に稼働していて空きがある → CA でも解消できる**

```
8 CPU ノード [ Pod ]        2 CPU ノード [ 空きあり ]
      ↓ Pod を移動して 8 CPU ノードを削除
                            2 CPU ノード [ Pod ]
```

**ケースB：小さいノードが稼働していない → CA では解消できない**

```
8 CPU ノード [ Pod ]     （2 CPU のノードグループは定義済みだが 0 台）
      ↓
      何も起きない
```

CA は「2 CPU のノードを 1 台作れば 8 CPU のノードを消せる」という判断をしません。理由は 2 つあります。

- **スケールアップのトリガーは Pending Pod だけ**。Pod は正常稼働中なので新ノードは作られない
- **スケールダウンの判定は「既存ノードへ移動できるか」だけ**。「新しく作れば消せる」は評価対象外

つまり CA には「**安いノードを作ってから高いノードを消す**」という一連の操作の概念がありません。
Karpenter の Consolidation はこれを 1 つの操作として実行します。

> **CA でも「作成時」のサイズ選択はできます**
> 複数のノードグループがある場合、CA は **expander**（`least-waste` / `price` / `priority` など）で
> どのグループを増やすかを選べます。つまり「新規作成時に適切なサイズを選ぶ」ことは可能です。
> できないのは「**稼働中のノードを、後からより小さいものに交換する**」ことです。

また CA では、置き換え先の小さいノードを**常時稼働させておく必要がある**（ケースA の前提）ため、
それ自体が待機コストになります。Karpenter は必要になったときに作るので、この待機コストが不要です。

## 補足：CA のスケールダウン条件と既定値

CA がノードを削除するのは、次の 3 つをすべて満たしたときです。

| 条件 | 起動オプション | 既定値 |
| --- | --- | --- |
| ノードの使用率が閾値未満 | `--scale-down-utilization-threshold` | **0.5**（50%） |
| 全 Pod を**既存ノード**へ移動可能 | （シミュレーションで判定） | — |
| その状態が継続 | `--scale-down-unneeded-time` | **10m** |

これらは **cluster-autoscaler の起動引数**として与えるため、クラスタ全体に一律で効きます。
Karpenter では **NodePool ごとに `disruption` で宣言的に**設定できます。

> **よくある誤解**
> 「CA は空のノードしか消せない」と言われることがありますが、**正確には誤り**です。
> ただし `kube-system` の Pod（PDB 無し）、ローカルストレージを使う Pod、
> コントローラーに属さない単体 Pod などが載っていると削除がブロックされるため、
> **運用実感としては「空にならないと消えない」状態になりやすい**、というのが実情です。

## 両者に共通して「できない」こと

ここは誤解されやすいので、発表時に触れておくと親切です。

### ① Pod の数そのものは増減しない

CA も Karpenter も **ノードを増減させるだけ**で、Deployment などの**レプリカ数は変更しません**。
Pod 数を増減させるのは **HPA（Horizontal Pod Autoscaler）** の役割です。

```
HPA        … Pod の数を増減させる
CA / Karpenter … Pod を載せるノードを増減させる
```

### ② 実際の CPU・メモリ使用率は見ていない

ノード追加・統合の判断は、主に Pod の **`resources.requests`** とスケジューリング制約に基づきます。
**実際の使用率を直接見て判断するわけではありません。**

そのため、次の 2 点が重要になります。

- **適切な Resource Request の設定**（requests が実態とかけ離れていると、判断も的外れになる）
- **HPA や VPA との組み合わせ**

## 選択の目安

| 状況 | おすすめ |
| --- | --- |
| 少数の標準化されたノード構成を安定運用したい | **Cluster Autoscaler** |
| ワークロードが多様で、インスタンス選択やコスト最適化を動的に行いたい | **Karpenter** |
| 固定的なシステム用ノードと、変動するアプリ用ノードを分けたい | **固定ノードグループ ＋ Karpenter の併用** |

> **本デモの構成はまさに 3 番目です。**
> KPO コントローラーを動かす既存ノードプール（固定）と、
> Karpenter が動的に作るノード（変動）を併用しています（[04](04-demo-scaleout.md)）。
